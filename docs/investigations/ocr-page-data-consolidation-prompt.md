# Investigation Prompt: Consolidate OCR Page Data (text + confidence + geometry) for a richer Page Data viewer and Assessment explainability

> Hand this to a fresh Claude Code session. It is an **investigation + design** task — produce a written plan and recommendations, do NOT implement yet. Ask clarifying questions if the scope is ambiguous, then deliver a plan (use ExitPlanMode).

## Background / motivation

The GenAI IDP Accelerator runs OCR per page and writes several **separate** S3 artifacts per page under `<output>/<doc>/pages/<page_id>/`:

- `image.jpg` — the page image
- `rawText.json` — the **full raw OCR response**. For Textract this is the complete Textract JSON, which is the ONLY place that holds **word/line bounding-box geometry** (`Geometry.BoundingBox`, `Polygon`) and per-block `Confidence`.
- `textConfidence.json` — a **token-reduced markdown table** of `| Text | Confidence |` (LINE-level), generated by `OcrService._generate_text_confidence_data()`. Geometry is deliberately stripped here to save tokens for the LLM.
- `result.json` — `{"text": "<markdown or plain text>"}` (the parsed text/markdown).

So today: **markdown** lives in `result.json`, **confidence** lives in `textConfidence.json`, and **geometry** lives only inside `rawText.json` (and only for Textract). These are not consolidated, have inconsistent granularity, and geometry is not exposed in a form the UI Page Data viewer or the Assessment step can easily consume.

Two consumers motivate consolidation:

**(a) An enhanced "Page Data" viewer.** Today the per-page viewer is a text/markdown + confidence-table modal (`src/ui/src/components/pages-panel/PageTextEditorModal.tsx`, with `MarkdownJsonViewer.tsx`) — see the "View Page 1 Text" modal with "Text + Markdown" / "Text + Confidence" tabs. We want it to be more like the **section-level Visual Editor** (`src/ui/src/components/document-viewer/VisualEditorModal.tsx` + `src/ui/src/components/common/PageImageViewer.tsx`) which shows the page image and can draw bounding boxes. The goal: a page viewer that shows the image, the text/markdown, per-line/word confidence, AND draws bounding boxes when geometry is available.

**(b) The Assessment step's `explainability_info`.** Assessment derives per-field confidence and geometry for extracted attributes. It reads OCR confidence via `AssessmentService._get_text_confidence_data()` (prefers `page.text_confidence_uri`, falls back to regenerating from `page.raw_text_uri`) and injects it into prompts as the `{OCR_TEXT_CONFIDENCE}` placeholder. It converts LLM-returned bboxes (0-1000 scale) to geometry via `_convert_bbox_to_geometry()` and writes `extraction_data["explainability_info"]`. If OCR geometry were available in a consistent, consolidated form, Assessment could potentially ground field confidence/geometry in real OCR data rather than (or in addition to) LLM-estimated boxes.

## Recent related work (read this first)

A new serverless **Mistral OCR** LambdaHook backend was just added (see memory `project_mistral_ocr_hook` and `samples/lambda-hook-inference/GENAIIDP-mistral-ocr-hook/`). As part of it:

- `OcrService._extract_bedrock_ocr_artifacts()` (in `lib/idp_common_pkg/idp_common/ocr/service.py`) was added so a LambdaHook OCR response carrying a top-level `textractBlocks` object (Amazon Textract response format) is persisted as `rawText.json` + a real `textConfidence.json`.
- The Mistral hook produces **per-line confidence** (averaged from per-word scores via `start_index`) and **paragraph-level geometry** (normalized 0-1 BoundingBox). It does NOT have per-word geometry (Mistral words carry no bbox), and sibling lines from one multi-line paragraph **share** a bounding box. WORD blocks carry confidence but no geometry.

This exposed the core granularity problem this investigation must address: **confidence and geometry are at different granularities, and differ by OCR backend** (Textract: per-word+per-line geometry & confidence; Mistral: per-line confidence + per-paragraph geometry; plain Bedrock LLM OCR: text only, no confidence/geometry).

## What to investigate and design

1. **Inventory the current per-page artifacts and their producers/consumers.** Map exactly what writes and reads `image.*`, `rawText.json`, `textConfidence.json`, `result.json`. Key files:
   - Producer: `lib/idp_common_pkg/idp_common/ocr/service.py` (3 backend paths: textract / bedrock(+LambdaHook) / none; plus `_process_page_with_image`, `_process_image_file_direct`, `_process_single_page_bedrock`, `_generate_text_confidence_data`, `_parse_textract_response`, `_extract_bedrock_ocr_artifacts`).
   - Model: `Page` dataclass in `lib/idp_common_pkg/idp_common/models.py` (`image_uri`, `raw_text_uri`, `parsed_text_uri`, `text_confidence_uri`).
   - Consumers: Assessment (`lib/idp_common_pkg/idp_common/assessment/service.py` — `_get_text_confidence_data`, `_convert_bbox_to_geometry`, `_extract_geometry_from_assessment`, `explainability_info`), the UI Page viewer (`pages-panel/PageTextEditorModal.tsx`, `document-viewer/MarkdownJsonViewer.tsx`), the section Visual Editor (`document-viewer/VisualEditorModal.tsx`, `common/PageImageViewer.tsx`), and any reporting/eval/export consumers (grep `text_confidence_uri`, `raw_text_uri`, `parsed_text_uri`).

2. **Define a consolidated, backend-agnostic per-page "OCR page data" schema** that carries, at a consistent granularity, for each text unit: `text`, `confidence`, and `geometry` (normalized 0-1 BoundingBox + optional Polygon), plus page dimensions and a backend/provenance tag. Decide the granularity model (e.g. LINE as the primary unit, with optional WORD children) and how to represent **missing** data per backend (Textract has word geometry; Mistral has only paragraph geometry; LLM OCR has neither). Consider Textract's PAGE/LINE/WORD + Relationships as the reference model and how to map each backend onto it. Decide whether confidence and geometry must share a unit or can be independently present.

3. **Decide file strategy.** Options to weigh (with pros/cons, migration cost, token budget impact on Assessment prompts, S3 object count, backward compatibility):
   - (A) New single consolidated artifact (e.g. `pageData.json`) alongside the existing files; keep existing files for back-compat.
   - (B) Extend `textConfidence.json` to optionally include geometry (risk: token bloat in the `{OCR_TEXT_CONFIDENCE}` prompt — measure it).
   - (C) Keep `rawText.json` as source of truth and add a lightweight derived geometry index.
   - Note: the assessment confidence table is intentionally token-reduced; any change must not blow up Assessment prompt token counts. Quantify.

4. **Backward compatibility & migration.** There are deployed stacks with existing documents. The `Page` model, AppSync schema, UI, Assessment, reporting, and export (`document-export.test.ts`) all read these URIs. Propose how to add new fields without breaking old documents, and whether a new `Page.<x>_uri` field is needed.

5. **Enhanced Page Data viewer design (UI).** Specify how to evolve `PageTextEditorModal` toward the `VisualEditorModal`/`PageImageViewer` pattern: show the page image, overlay bounding boxes (when geometry present), show per-line/word confidence (color-coded?), and degrade gracefully when a backend provides no geometry. Identify the AppSync/GraphQL and data-fetch changes needed to deliver geometry to the client.

6. **Assessment explainability integration.** Propose whether/how Assessment should use consolidated OCR geometry to ground `explainability_info` (field-level confidence + bounding boxes), vs. today's LLM-estimated 0-1000 bboxes. Note `_convert_bbox_to_geometry` expects 0-1000; consolidated OCR geometry is 0-1 — reconcile coordinate spaces.

7. **Cross-backend consistency matrix.** Produce a table: for Textract / Mistral-hook / Chandra-hook / plain-Bedrock-LLM OCR / `none`, what text, confidence granularity, and geometry granularity each provides, and how each maps onto the proposed schema.

## Deliverables
